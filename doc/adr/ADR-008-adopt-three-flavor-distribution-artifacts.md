# ADR-008: Adopt Three-Flavor Distribution Artifacts

Date: 2026-09-21

## Status

Accepted

## Context

The repository currently maintains source beneath `src/` and commits a generated
root-level `upload_sarif_to_defectdojo.bash` compatibility artifact.  ADR-005
introduced that split while explicitly deferring the broader multi-artifact
distribution model to issue #251.

The related Bash projects now use a consistent three-flavor distribution model:

- a fully documented development artifact;
- a conventional consumer artifact with full-line comments removed; and
- a minified consumer artifact generated with pinned Bash-Minifier bytes.

Issue #251 requests that this repository adopt that model, add adjacent SHA-256
companions, expose all six files as CI/release artifacts, and retain build
provenance such as version, source commit, and source-revision date.

The current uploader has one additional compatibility constraint: existing users
may directly download
`https://raw.githubusercontent.com/wesley-dean/upload-sarif-to-defectdojo/main/upload_sarif_to_defectdojo.bash`.
That path must remain usable after the new `dist/` model is introduced.

The runtime help implementation also currently extracts its overview from
full-line Doxygen comments in the executing file.  A genuinely comment-stripped
ordinary artifact would therefore change `--help` behavior unless help text is
moved into executable maintained data.

## Decision Drivers

- Use one deterministic source-to-distribution pipeline for every shipped Bash
  representation.
- Preserve Doxygen documentation in a review-oriented assembled artifact.
- Provide a conventional comment-stripped consumer artifact.
- Provide a minified artifact generated by pinned, reviewable tooling.
- Keep every artifact standalone and independent of `vendor/` at runtime.
- Preserve the historical root raw-download path.
- Produce portable adjacent SHA-256 companions.
- Keep build provenance available in every artifact flavor.
- Run the same observable behavior suite against all three artifact flavors.
- Keep `dist/` derivative output outside source/security scanning.
- Validate release candidates before granting release-write authority.

## Decision

The canonical maintained uploader source remains:

`src/upload_sarif_to_defectdojo.bash`

Generated distribution state SHALL live beneath `dist/` and SHALL NOT be
committed.  The build SHALL produce exactly these six distribution files:

- `dist/upload_sarif_to_defectdojo.dev.bash`
- `dist/upload_sarif_to_defectdojo.dev.bash.sha256`
- `dist/upload_sarif_to_defectdojo.bash`
- `dist/upload_sarif_to_defectdojo.bash.sha256`
- `dist/upload_sarif_to_defectdojo.min.bash`
- `dist/upload_sarif_to_defectdojo.min.bash.sha256`

The root `upload_sarif_to_defectdojo.bash` file SHALL remain committed for
backward compatibility and SHALL be a byte-for-byte mirror of
`dist/upload_sarif_to_defectdojo.bash` after an ordinary development build.
It remains the file copied by the existing container image and the historical raw
download path.

The fully documented development artifact SHALL be assembled first from:

1. one generated provenance header;
2. executable build metadata variables;
3. the pinned `bashlog.dev.bash` dependency with its shebang removed; and
4. the maintained uploader source with its shebang removed.

The build metadata variables SHALL carry project name, version, build date, and
build commit so provenance survives subsequent removal of full-line comments.
The default development version is `0.0.0-dev`.  Release workflows SHALL pass
the calculated semantic version explicitly.

The ordinary artifact SHALL be derived only from the development artifact by
removing full-line comments while preserving the shebang and executable content.
Inline comments are executable-line content and are not required to be stripped.

The minified artifact SHALL be derived only from the ordinary artifact by the
pinned Bash-Minifier dependency.

To make those transformations behavior-preserving, the user-facing help overview
SHALL be maintained as executable data rather than reconstructed from Doxygen
comments at runtime.  All three artifact flavors SHALL therefore expose the same
help contract even though only the development artifact retains full-line source
documentation.

The repository SHALL replace its ordinary bashlog build dependency with the
documented release artifact:

- release: `bashlog v0.0.18`;
- artifact: `bashlog.dev.bash`;
- destination: `vendor/bashlog.dev.bash`; and
- SHA-256:
  `d916f73092f8bc07b917910e5a54ada04ccf8259a0af01ad500084c5a0f91ea5`.

The maintained source MAY source that development dependency when executed
directly after dependency preparation.  Generated artifacts embed it and SHALL
not require it at runtime.

The repository SHALL pin the same Bash-Minifier revision used by related Bash
projects:

- upstream: `Zuzzuc/Bash-minifier`;
- commit: `9c824e20815a5bca2153ec25ecc02a4edea1430e`;
- artifact: `Minify.sh`;
- destination: `vendor/bash-minifier.bash`; and
- SHA-256:
  `93cb422360db4cc410d19b068eb074da020a4a743f0eebc9c442d1e5acd90e9b`.

Both dependencies SHALL remain managed by the existing bashdeps manifest.
`make build` SHALL consume prepared dependency bytes and SHALL remain
network-free.

Each executable artifact SHALL receive an adjacent `.sha256` file in standard
`sha256sum` format using only the artifact basename.  Legacy `.256` checksum
names are not part of the contract.

The canonical behavior suite SHALL run against all three `dist/*.bash` artifact
flavors.  Tests SHALL accept an explicit artifact path through test harness state
rather than assuming the root compatibility file.  CI SHALL additionally verify:

- exactly three executable Bash artifacts and three checksum companions;
- checksum validity;
- root compatibility-file byte equality with the ordinary artifact;
- deterministic rebuild bytes when version/provenance inputs are unchanged;
- non-identity of ordinary and minified artifacts;
- the presence of Doxygen documentation in the development artifact;
- the absence of full-line generated comments in the ordinary artifact;
- standalone execution without `vendor/`; and
- Bash 4.3 compatibility for every artifact flavor.

`dist/` SHALL be ignored by Git and explicitly excluded from MegaLinter and
other repository-owned source scanning.  Generated distribution bytes are
validated through build determinism, checksums, syntax/compatibility checks, and
the behavior suite rather than rescanned as maintained source.

The semantic-version release workflow SHALL calculate the candidate version
without creating a tag, build and validate the exact six release files in a
read-only validation job, and transfer only those validated files to a separate
publication job.  The publication job SHALL not check out or rebuild source.
It SHALL verify the transferred file set and checksums again, then create the
release/tag and attach all six files.

The container publication path remains based on the committed root compatibility
artifact and therefore continues to consume the ordinary representation.

This decision supersedes only the source/distribution clauses of ADR-002 and
ADR-005 that describe a single generated public artifact.  Their runtime,
testing, dependency, logging, and compatibility decisions remain in force where
not refined here.

## Alternatives Considered

### Replace the historical root download with a dist URL

Rejected because existing curl consumers would break or require migration for no
runtime benefit.  Keeping a committed mirror is small and testable.

### Keep bashlog.bash as the embedded dependency in the development artifact

Rejected because the development artifact is intended to preserve assembled
documentation.  Using the released `bashlog.dev.bash` artifact gives reviewers
the documented dependency representation while the ordinary build transformation
still produces comment-stripped consumer bytes.

### Build the three flavors independently from maintained source

Rejected because independent pipelines can drift.  Development to ordinary to
minified establishes one auditable transformation chain.

### Keep help text dependent on source comments

Rejected because the ordinary artifact must remove full-line comments.  Runtime
behavior must not depend on which documentation representation was shipped.

### Commit dist/

Rejected because these are deterministic derivative release products.  Committing
them would duplicate the maintained source and create avoidable scan/review noise.

### Let the release job rebuild artifacts

Rejected because a privileged publication job should receive already validated
candidate bytes rather than execute the full repository build surface with
release-write authority.

## Consequences

Developers must prepare dependencies before building or running the complete
artifact behavior suite.  `make test` remains network-free but now consumes
prepared build dependencies because it builds and exercises the three generated
flavors.

The committed root compatibility file remains in ordinary repository diffs when
maintained source changes, while the six `dist/` files remain ignored derivative
state.

Release consumers gain documented, ordinary, and minified choices plus portable
checksums.  Existing raw-download and container consumers retain their current
path and ordinary behavior.

The semantic-version workflow becomes a validate-then-publish pipeline rather
than creating the tag before candidate artifacts have been exercised.
